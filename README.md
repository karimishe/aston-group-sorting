# aston-group-sorting

Групповой учебный проект на Java. Разрабатываем консольное приложение, которое получает автомобили, сортирует их по выбранному правилу и показывает результат.

Программа работает в цикле: после действия пользователь возвращается в меню, а для завершения выбирает «Выход».

## Состояние проекта

Работает минимальный сценарий каркаса: загрузка автомобилей из файла, сортировка вставками и просмотр исходной коллекции и результата. Пользователь задаёт путь и количество записей, а затем выбирает действия в меню. Неверный ввод можно исправить, ошибка файла сохраняет прежние данные и результат, обычный выход выполняется пунктом `0`. Есть модель `Car` с Builder, коллекция `MyArrayList<T>`, пять общих интерфейсов и ручные тесты готовых частей.

Через `Modules` подключены `FileCarSource`, `CarAllFieldsComparator` и `InsertionSort<Car>`. Порядок сравнения фиксирован: мощность, затем модель и год при равенстве предыдущих полей. Такой приоритет — решение проекта; условие не задаёт его. Исходная коллекция сохраняется: алгоритму передаётся копия контейнера. Перед началом работы команды каркас нужно объединить в `main`. Участники добавят ручной и случайный ввод, отдельные компараторы и два других алгоритма, затем перейдут к допам. Состав и критерии готовности описаны в [каркасе приложения](docs/scaffold.md), обязанности участников — в [плане разработки](docs/development-plan.md).

Рабочая модель — автомобиль `Car` с тремя полями:

| Поле | Что хранит | Тип Java |
| --- | --- | --- |
| `power` | Мощность | `int` — целое число |
| `model` | Название модели | `String` — строка |
| `productionYear` | Год выпуска | `int` — целое число |

Условие позволяет выбрать любой один класс. Автомобиль — наш выбор для этого проекта.

## Что должна делать программа

Основная часть:

- Принимать количество автомобилей и способ заполнения: вручную, из файла или случайно.
- Проверять входные данные и понятно сообщать об ошибках.
- Создавать автомобили через собственный Builder.
- Сортировать собственными алгоритмами с переключением через Strategy.
- Поддерживать сравнение по каждому полю и базовый порядок по трём полям.
- Показывать результат и продолжать работу до выбора выхода.

Дополнительные возможности: сортировка только чётных значений, добавление результата в файл, заполнение через Stream, собственная коллекция и многопоточный подсчёт вхождений. Подробные условия перечислены отдельно; наличие пункта в плане не означает, что он уже реализован.

## Архитектура коротко

Разделяем приложение на небольшие части с понятными обязанностями. Путь данных: **ввод → проверка и создание автомобилей → коллекция → сортировка → результат**.

- **Меню (`ConsoleApplication`)** спрашивает, что сделать, вызывает нужные части и показывает результат или ошибку. После действия снова ждёт выбор пользователя.
- **Автомобиль (`Car`) и Builder** отвечают за данные одного автомобиля. Builder проверяет поля и создаёт объект.
- **Источники данных (`DataSource`)** получают автомобили вручную, из файла или случайным образом. Все возвращают коллекцию в одном формате.
- **Коллекция (`MyArrayList<T>`)** хранит объекты. `T` — тип её элементов; в нашем приложении это `Car`.
- **Компаратор (`Comparator`)** задаёт правило сравнения двух автомобилей: например, по мощности или по всем трём полям.
- **Алгоритм (`SortStrategy<T>`)** переставляет объекты в коллекции по этому правилу. Уже работает сортировка вставками; команда добавит сортировки выбором и пузырьком. Подключение алгоритма через общий интерфейс — основа паттерна «Стратегия»; выбор между несколькими алгоритмами появится вместе с их реализациями.

Чтобы сменить поле сортировки, передаём другой компаратор. Сам алгоритм менять не требуется. Для другого типа объектов понадобятся своя модель, ввод и правила сравнения; коллекцию и алгоритмы можно использовать повторно.

Дополнительные возможности подключаем отдельными модулями с заранее согласованными методами. Это позволяет участникам работать независимо. Подробная схема и примеры — в [описании архитектуры](docs/architecture.md), уже добавленные интерфейсы — в [договорах модулей](docs/contracts.md).

## Как открыть и запустить проект

Получить локальную копию репозитория можно командой:

```sh
git clone https://github.com/karimishe/aston-group-sorting.git
```

### IntelliJ IDEA

1. Выберите **File → Open** и откройте папку `aston-group-sorting`.
2. В **File → Project Structure → Project** выберите установленный **JDK** — комплект инструментов для сборки и запуска Java. Для команд из раздела ниже нужен JDK 9 или новее. В **Language level** выберите **8**, чтобы придерживаться синтаксиса Java 8.
3. Убедитесь, что папка `src` отмечена как исходники. Если нет, нажмите на неё правой кнопкой и выберите **Mark Directory as → Sources Root**.
4. Откройте [Main.java](src/sorting/app/Main.java) и нажмите зелёную кнопку рядом с методом `main` → **Run 'Main.main()'**.

Если IDEA не создала Java-модуль, откройте **Project Structure → Modules → + → Import Module**, укажите корень проекта и выберите создание модуля из существующих исходников. Его корнем должна быть папка `aston-group-sorting`, а папкой исходников — `src`.

Аргументы программы не нужны. Рабочая папка (**Working directory**) в конфигурации запуска — корень `aston-group-sorting`. После запуска выберите вкладку консоли, введите номер пункта и нажмите Enter. Консольный ввод читается в UTF-8. Относительные пути, например `examples/cars-valid.txt`, отсчитываются от рабочей папки. Можно указать полный путь; кавычки вокруг него вводить не нужно.

### Терминал

Выполните команды из корня `aston-group-sorting`:

```sh
javac --release 8 -encoding UTF-8 -d out src/sorting/*/*.java
java -cp out sorting.app.Main
```

`javac` компилирует исходники в файлы `.class`. Шаблон `src/sorting/*/*.java` выбирает Java-файлы из текущих пакетов, включая интерфейсы каркаса. Параметр `-d out` задаёт папку для результата, а `--release 8` — совместимость с Java 8. `java -cp out` запускает программу, используя классы из папки `out`.

Программа использует обычный Java и стандартную библиотеку, без Maven, Gradle и сторонних зависимостей. Сборка и запуск из терминала проверены на **Oracle JDK 25.0.4.1**. Запуск на самой JDK 8 отдельно не проверялся. Компилятор JDK 25 может предупредить, что целевая версия 8 устарела; это предупреждение не мешает сборке.

При запуске отображается меню:

```text
Приложение сортировки автомобилей

Меню:
1. Загрузить автомобили из файла
2. Отсортировать автомобили
3. Показать исходную коллекцию
4. Показать результат сортировки
0. Выход
Ваш выбор:
```

Для проверки всего сценария введите по очереди: `1`, `examples/cars-sort.txt`, `6`, `3`, `2`, `4`, `0`. Программа загрузит шесть автомобилей, покажет исходные данные по команде `3`, отсортирует их по команде `2`, покажет результат по команде `4` и завершится по команде `0`. После действия меню появляется снова.

До загрузки команда `2` предлагает сначала получить данные. До сортировки команда `4` сообщает, что результата ещё нет. Повторная сортировка разрешена. Успешная новая загрузка сбрасывает результат, чтобы он не относился к прежним данным; ошибка загрузки сохраняет обе коллекции.

При запросе команды или количества пустая строка, текст, дробное число или число вне диапазона не завершают приложение: оно объясняет ошибку и повторяет запрос. При закрытии потока ввода до команды `0` продолжать чтение невозможно. Это технический обрыв: `Main` печатает ошибку в поток ошибок и завершает процесс с кодом `1`. При обычном выходе код равен `0`. Результаты проверок процесса, включая обрыв при запросах пути и количества, сохранены в [file-load-process-checks.txt](examples/file-load-process-checks.txt).

Файл должен быть в UTF-8 без заголовка, одна запись `мощность;модель;год` на строку. Пример — [cars-valid.txt](examples/cars-valid.txt). Количество должно быть положительным. Проверяется весь файл: при лишних корректных записях выбираются первые N; при нехватке записей, пустой или неверной строке загрузка отклоняется. Ошибка данных содержит номер строки. Предыдущая коллекция заменяется только после успешной загрузки.

Демонстрация загрузки, неверной длины и плохого файла воспроизводится так:

```sh
java -cp out sorting.app.Main < examples/file-load-input.txt
```

В [file-load-input.txt](examples/file-load-input.txt) записаны вводимые строки, а в [file-load-session.txt](examples/file-load-session.txt) — фактический вывод программы. После успешной загрузки пример пробует прочитать [cars-invalid.txt](examples/cars-invalid.txt): отрицательная мощность во второй строке отклоняет весь файл, даже когда запрошена одна запись. Повторный просмотр показывает прежние данные. При перенаправлении ввод не отображается в выводе автоматически.

Полный сценарий с сортировкой и ошибкой файла:

```sh
java -cp out sorting.app.Main < examples/sort-input.txt
```

В [cars-sort.txt](examples/cars-sort.txt) есть одинаковые мощности, модели и повторяющиеся записи, чтобы проверить все три поля. [sort-input.txt](examples/sort-input.txt) содержит команды, [sort-session.txt](examples/sort-session.txt) — фактический вывод. Пример показывает попытку сортировки до загрузки, успешную сортировку, сохранение исходного порядка и сохранение результата после плохого файла.

Исторические примеры предыдущих шагов сохранены отдельно: [первый запуск](examples/first-run.txt), [Builder](examples/car-builder.txt), [меню с заглушками](examples/menu-session.txt) и [проверки завершения меню](examples/menu-process-checks.txt). Старый `menu-input.txt` относится к версии без загрузки файла и не подходит для текущего меню.

### Что делает первый класс

- `package sorting.app;` объединяет классы по назначению. Пакету соответствует путь `sorting/app/` внутри `src`.
- `public class Main` объявляет класс `Main`; его имя совпадает с именем файла `Main.java`.
- `public static void main(String[] args)` — метод, с которого Java начинает выполнение программы. `args` содержит аргументы запуска; сейчас они не используются.
- `System.out.println(...)` выводит строку в консоль и переводит курсор на следующую строку.

### Как работают меню и чтение ввода

- [Main](src/sorting/app/Main.java) создаёт один читатель консоли, `Modules` и приложение. `InputStreamReader` превращает байты из `System.in` в символы. Технические ошибки чтения обрабатываются здесь.
- [ConsoleInput](src/sorting/input/ConsoleInput.java) читает строки через один `BufferedReader`. Метод `readInt` преобразует строку в целое число и проверяет диапазон. После ошибки запрашивает значение повторно.
- [ConsoleApplication](src/sorting/app/ConsoleApplication.java) показывает меню и выбирает действие через `switch`. `break` завершает обработку текущего пункта, после чего цикл `while` повторяется. `return` в пункте `0` завершает метод `run()`.

Ввод и вывод передаются через конструкторы. В обычном запуске это консоль; в тестах — строки и буфер вывода. Поэтому проверки могут воспроизводить последовательность команд без ручного набора и без замены глобальных потоков Java. Будущий ручной источник будет использовать тот же `ConsoleInput`.

### Как устроена загрузка файла

- [CarLineParser](src/sorting/source/CarLineParser.java) разбирает одну строку: делит её по `;`, проверяет число полей, преобразует мощность и год в числа и вызывает Builder. `split(";", -1)` сохраняет пустое последнее поле, чтобы отсутствие года тоже обнаруживалось.
- [FileCarSource](src/sorting/source/FileCarSource.java) реализует `DataSource<Car>`: читает файл построчно, передаёт строки парсеру и собирает первые N автомобилей. При ошибке добавляет номер строки. Конструкция `try` с ресурсом закрывает файл и при успехе, и при исключении.
- [Modules](src/sorting/app/Modules.java) выбирает реализацию: метод `fileSource(path)` пока возвращает `new FileCarSource(path)` как `DataSource<Car>`. Позже здесь можно подключить версию через Stream.
- Меню спрашивает путь и длину, вызывает `load(length)` и сохраняет результат. Если чтение или проверка не удались, присваивание новой коллекции не выполняется.

Таким образом, меню управляет действиями, источник работает с файлом, парсер — с форматом строки, а Builder — с допустимостью полей автомобиля.

### Как создаётся автомобиль

[Car](src/sorting/model/Car.java) находится в пакете `sorting.model`. Строка `import sorting.model.Car;` позволяет обращаться к классу по короткому имени. Файловый парсер и будущие источники создают автомобили так же, как в этом примере:

```java
Car car = new Car.Builder()
        .power(150)
        .model("Kia")
        .productionYear(2020)
        .build();
```

`Builder` хранит значения до создания автомобиля. Методы `power`, `model` и `productionYear` возвращают тот же Builder (`return this`), поэтому вызовы можно записать цепочкой. Метод `build()` проверяет данные и возвращает новый `Car`. При ошибке он выбрасывает `IllegalArgumentException` с объяснением причины.

Мощность должна быть положительной, модель — непустой после `trim()` и без `;`, `\r`, `\n`, год — от 1900 до текущего. `trim()` удаляет пробелы по краям строки. Все три поля обязательны.

Данные готового `Car` закрыты через `private` и задаются один раз через `final`. Методы `getPower()`, `getModel()` и `getProductionYear()` позволяют их читать. Сортировка позже будет переставлять целые объекты, сохраняя данные каждого автомобиля.

### Как сравниваются автомобили

[CarAllFieldsComparator](src/sorting/compare/CarAllFieldsComparator.java) реализует стандартный интерфейс `Comparator<Car>`. Его метод `compare(first, second)` сравнивает два автомобиля по очереди:

1. Мощность — по возрастанию.
2. Если мощность одинакова, модель — через `String.compareTo`, с учётом регистра.
3. Если модель тоже одинакова, год выпуска — по возрастанию.

Например, `100;Volvo;2022` идёт раньше `150;Audi;2018`: мощность важнее модели. Для одинаковой мощности `150;Audi;2022` идёт раньше `150;Kia;2018`. Год влияет на порядок только при одинаковых мощности и модели.

Результат `compare` — отрицательное число, если первый автомобиль должен идти раньше; положительное, если позже; `0`, если совпадают все три поля. Важен знак, а не точное число. Сам компаратор не переставляет элементы коллекции — его вызывает алгоритм сортировки.

`Integer.compare` сравнивает целые числа, `String.compareTo` — строки. Готовая сортировка здесь не используется. Компаратор не принимает `null`. Нулевой результат для разных объектов означает равенство по правилу сравнения; собственного `Car.equals` пока нет.

### Как работает сортировка вставками

[InsertionSort<T>](src/sorting/algorithm/InsertionSort.java) проходит коллекцию слева направо, начиная со второго элемента. Перед каждым шагом часть слева уже упорядочена. Алгоритм сохраняет текущий элемент, сдвигает более крупные элементы слева на одну позицию вправо и помещает сохранённый элемент на освободившееся место.

Например, для мощностей `150, 100, 120`: сначала `100` вставляется перед `150`, затем `120` вставляется между `100` и `150`. В приложении перемещаются ссылки на целые автомобили; что считать «больше», определяет компаратор.

Класс реализует `SortStrategy<T>` и не обращается к полям `Car`. Его можно использовать с числами или строками, передав подходящий компаратор. Пустая коллекция и один элемент допустимы. Готовые методы сортировки не используются.

В меню операция соединяет части так:

```java
MyArrayList<Car> result = cars.copy();
SortStrategy<Car> strategy = modules.sortStrategy();
Comparator<Car> comparator = modules.carComparator();
strategy.sort(result, comparator);
sortedCars = result;
```

`cars` хранит исходные данные, `sortedCars` — последний успешный результат. Присваивание результата выполняется после сортировки. При исключении во время операции меню сообщает причину и сохраняет предыдущие коллекции. `copy()` создаёт отдельный контейнер с теми же ссылками на неизменяемые автомобили.

`Modules.sortStrategy()` сейчас возвращает `InsertionSort<Car>`, `carComparator()` — `CarAllFieldsComparator`. Здесь тимлид будет подключать новые реализации команды. Чтобы добавить другой алгоритм, нужно выполнить договор `SortStrategy<T>`; сам код загрузки от него не зависит.

### Что даёт каркас участнику

Общая коллекция уже работает:

```java
MyArrayList<Car> cars = new MyArrayList<>();
cars.add(car);
Car first = cars.get(0);
```

В этом примере `car` — ранее созданный автомобиль, а `MyArrayList` нужно импортировать из `sorting.collection`. Коллекция хранит объекты, но не знает правил их сравнения.

Интерфейс фиксирует метод будущей реализации. Например, `SortStrategy<T>` содержит:

```java
void sort(MyArrayList<T> items, Comparator<T> comparator);
```

Здесь нет тела метода: автор алгоритма пишет его в своём классе. Все алгоритмы получают одну и ту же коллекцию и стандартный интерфейс правила сравнения. Готовые `InsertionSort<T>` и `CarAllFieldsComparator` служат образцами для остальных реализаций команды.

Аналогично зафиксированы договоры источника `DataSource`, чётного режима `EvenSorter`, записи `ResultWriter` и подсчёта `OccurrenceCounter`. Подробности и оставшиеся зависимости — в [договорах модулей](docs/contracts.md).

## Как запустить тесты

В IntelliJ IDEA отметьте папку `test` через **Mark Directory as → Test Sources Root**. Запустите `main` в классах `CarTest`, `MyArrayListTest`, `ConsoleInputTest`, `ConsoleApplicationTest`, `CarLineParserTest`, `FileCarSourceTest`, `CarAllFieldsComparatorTest` и `InsertionSortTest` внутри этой папки.

Из терминала, находясь в корне проекта:

```sh
javac --release 8 -encoding UTF-8 -d out src/sorting/*/*.java test/sorting/*/*.java
java -cp out sorting.model.CarTest
java -cp out sorting.collection.MyArrayListTest
java -cp out sorting.input.ConsoleInputTest
java -cp out sorting.app.ConsoleApplicationTest
java -cp out sorting.source.CarLineParserTest
java -cp out sorting.source.FileCarSourceTest
java -cp out sorting.compare.CarAllFieldsComparatorTest
java -cp out sorting.algorithm.InsertionSortTest
```

Тесты модели проверяют создание, границы значений, отсутствующие поля, недопустимые символы и повторное использование Builder. Тесты коллекции проверяют добавление, чтение, замену, расширение внутреннего массива, ошибки индексов и `null`, а также независимость копии. Проверки консоли воспроизводят неверные числа, повтор меню, явный выход, конец ввода, загрузку и сохранение прежних данных после ошибки. Тесты парсера и файлового источника проверяют формат, UTF-8, кириллицу, пустой и короткий файл, неправильные строки, лишние записи и ошибки чтения. Они создают и удаляют временные файлы, не меняя примеры в репозитории.

Тесты компаратора проверяют приоритет каждого поля, оба направления сравнения, одинаковые поля разных объектов, регистр, кириллицу, границы мощности и года, а также `null`.

Тесты алгоритма проверяют пустую и одноэлементную коллекции, прямой, обратный и смешанный порядок, повторы, границы чисел, другие типы и компараторы, сохранение ссылок и исходного контейнера при сортировке копии. Тесты меню дополнительно проверяют весь путь от файла до результата, повторную сортировку, сброс результата при новой загрузке и его сохранение после ошибочной.

При нарушении ожидаемого поведения тест завершается с `AssertionError`; дополнительные библиотеки и параметр `-ea` не нужны. Пройдено 249 проверок: модель — 31, коллекция — 34, ввод — 16, меню — 57, парсер — 31, файловый источник — 29, компаратор — 19, сортировка — 32.

Фактические результаты сохранены в [car-tests.txt](examples/car-tests.txt), [collection-tests.txt](examples/collection-tests.txt), [console-input-tests.txt](examples/console-input-tests.txt), [console-application-tests.txt](examples/console-application-tests.txt), [car-line-parser-tests.txt](examples/car-line-parser-tests.txt), [file-source-tests.txt](examples/file-source-tests.txt), [car-all-fields-comparator-tests.txt](examples/car-all-fields-comparator-tests.txt) и [insertion-sort-tests.txt](examples/insertion-sort-tests.txt). Интерфейсы модулей проверены компиляцией всего проекта; их будущие реализации должны получить собственные тесты поведения.

## Как работаем

Добавляем небольшие законченные изменения. Сначала проверяем их локально, затем сохраняем отдельным коммитом и передаём на просмотр через Pull Request — запрос на объединение ветки.

У каждого участника должна быть своя ветка с кодом. Готовые изменения объединяем в `main`. Правила работы с ветками, критерии готовности и порядок передачи незавершённой задачи описаны в [плане разработки](docs/development-plan.md).
