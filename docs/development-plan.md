# План работы команды

В команде пять человек, включая тимлида Каримова Ильдара. Имена остальных участников и сроки нужно закрепить в задачах репозитория. Ниже участники обозначены номерами ролей.

Сначала завершаем основное задание: три источника данных, сравнение по каждому полю и по всем полям, выбор алгоритма и вывод результата. Затем добавляем дополнительные функции и готовимся к защите. Три алгоритма — решение команды; их количество в условии не задано.

## Текущее состояние

Рабочий каркас готов: меню, загрузка из файла, сравнение по трём полям, сортировка вставками и просмотр коллекций. Для этих частей есть тесты.

Ручной ввод, генератор, сортировки выбором и пузырьком, сравнение по отдельным полям пока отмечены в меню как нереализованные. Выбор такого пункта возвращает в главное меню. Перед началом задач получите актуальный `main` после объединения доработок меню и подключения модулей.

Состав каркаса описан в [scaffold.md](scaffold.md), интерфейсы и правила обработки ошибок — в [contracts.md](contracts.md). Команды запуска приложения и тестов находятся в [README](../README.md).

## Основное задание

Каждый участник пишет свою реализацию и тесты в отдельных файлах. Для подключения заменяет `return null` в своём методе `Modules` на создание объекта. Меню определяет доступность автоматически; `Main` и `ConsoleApplication` менять не нужно. Методы подключения перечислены в [контрактах](contracts.md#подключение).

| Участник | Задача и файлы | Что проверить | Ветка |
| --- | --- | --- | --- |
| 1. Каримов Ильдар | Каркас, общие интерфейсы и меню; ревью PR и координация команды | Совместная работа модулей после объединения PR | `feature/core`, доработка подключения — `feature/menu-wiring` |
| 2 | Ручной ввод: `ManualCarSource`, `CarConsoleReader`; сравнение по модели: `CarModelComparator` | Ровно заданное число автомобилей; повтор ввода после ошибки; валидация Builder; равные модели и учёт регистра | `feature/manual-input` |
| 3 | Генератор: `RandomCarSource`, `CarGenerator`; сравнение по году: `CarProductionYearComparator` | Размер коллекции и допустимость объектов; неположительная длина; разные и одинаковые годы | `feature/random-input` |
| 4 | Сортировка выбором: `SelectionSort<T>`; сравнение по мощности: `CarPowerComparator` | Пустая коллекция, один элемент, повторы, прямой и обратный порядок; крайние допустимые значения мощности | `feature/selection-sort` |
| 5 | Пузырьковая сортировка: `BubbleSort<T>`; тесты совместной работы модулей | Граничные случаи алгоритма; загрузка → сортировка → результат; повторные операции и сохранение данных после ошибки | `feature/bubble-sort` |

Источники реализуют `DataSource<Car>`, алгоритмы — `SortStrategy<T>`, компараторы — `Comparator<Car>`. Образцы уже есть: `FileCarSource`, `InsertionSort<T>` и `CarAllFieldsComparator`.

`CarConsoleReader` отвечает за ввод одного автомобиля и использует общий `ConsoleInput`, переданный из меню. Второй читатель консоли создавать не нужно. `CarGenerator` создаёт один случайный автомобиль. Позже эти два класса вместе с готовым `CarLineParser` понадобятся для заполнения через Stream.

Алгоритмы получают компаратор извне, сохраняют размер коллекции, сами объекты и число повторений. Каждый автор проверяет свой алгоритм с разными компараторами и другим типом данных, например `Integer`. Готовые сортировки и поиск не используем; ожидаемые последовательности в тестах задаём явно.

Участник 5 начинает проверку общего сценария с файлового источника. Ручной и случайный ввод добавляет в проверки после их подключения. Его тесты не заменяют тесты остальных участников.

## Работа с ветками и Pull Request

Каждый разработчик пишет тесты для своей части и сдаёт изменения кода через Pull Request (PR) из своей ветки в `main`. PR — запрос на проверку и объединение изменений. Напрямую в `main` код не отправляем.

Имена веток в таблице предложены для задач; это не список уже созданных веток.

1. Получить актуальный `main`, создать свою ветку и закрепить задачу.
2. Реализовать модуль, подключить его в своём методе `Modules` и добавить тесты в ту же ветку. Проверить сборку, свои и существующие тесты, запуск функции через меню. Сохранить изменения коммитами.
3. Отправить ветку на GitHub и открыть PR в `main`. В описании указать, что сделано, команды запуска тестов и фактические результаты. Назначить тимлида на проверку. Незавершённую работу можно показать в черновом PR.
4. Исправить замечания после проверки кода и повторно запустить тесты. Новые коммиты отправлять в ту же ветку — они попадут в уже открытый PR.
5. Если `main` изменился, получить новые изменения в свою ветку, разрешить конфликты и повторить проверки. После ревью тимлид объединяет PR и проверяет общий сценарий.

В `Modules` каждый меняет только методы своей задачи. Не переоформляем весь файл и не меняем соседние подключения: так изменения проще объединить. Новые тесты добавляем в отдельные классы, если для них не требуется менять существующие проверки.

По заданию веток с кодом должно быть не меньше участников. К сдаче все рабочие ветки должны быть объединены в `main`.

### Тесты своей части

Тесты храним в `test/sorting/` в пакете, соответствующем проверяемому классу: например, `SelectionSortTest` в `test/sorting/algorithm/`. Это обычные Java-классы с `main` и `AssertionError` при неудачной проверке. Команды компиляции и запуска есть в [README](../README.md#тесты); при добавлении нового тестового класса дополняем список команд.

Проверяем обычную работу, граничные случаи и неверные данные по контракту модуля. При исправлении ошибки добавляем тест, который воспроизводит её и проверяет исправление. Ручной запуск приложения дополняет эти тесты, но не заменяет их.

Задача завершена, когда реализация соблюдает контракт, тесты проходят, PR проверен тимлидом, а код объединён и работает в приложении. Автор должен уметь объяснить свой код.

## Дополнительные задания

Начинаем после основной части. Перед стартом подтверждаем распределение с учётом загрузки участников. Для каждого дополнения создаём отдельную ветку от актуального `main`.

| Участник | Задача | Основные проверки | Ветка |
| --- | --- | --- | --- |
| 2 | № 2: запись результатов в конец файла через `ResultWriter<Car>` | Старое содержимое сохраняется; два добавления подряд; UTF-8 и кириллица; файл без последнего перевода строки; ошибка пути | `feature/file-output` |
| 3 | № 4: многопоточный подсчёт совпадений через `OccurrenceCounter<T>` с выводом в консоль | Ноль, одно и несколько совпадений; разные объекты с одинаковыми полями; неверное и избыточное число потоков; завершение потоков и прерывание | `feature/parallel-count` |
| 4 | № 3 и `3*`: заполнение своей коллекции через Stream из всех трёх источников | Те же контракты, что у обычных источников; размер коллекции; плохой и короткий файл; неверный ручной ввод; допустимость случайных объектов | `feature/stream-input` |
| 5 | № 1: сортировка чётных значений мощности через `EvenSorter<T>` | Чётные значения идут по возрастанию; нечётные объекты остаются на прежних индексах; смешанные значения, только чётные или нечётные, повторы; работа со всеми алгоритмами | `feature/even-sort` |

Для Stream-источников нужны общие `CarConsoleReader`, `CarLineParser` и `CarGenerator`. Правила заполнения описаны в [контрактах](contracts.md). Пункт `3*` проверяем вместе с заполнением через Stream.

В подсчёте совпадением считаем одинаковые значения всех трёх полей автомобиля. Способ сравнения и устройство многопоточной работы выбирает автор задания № 4. Необходимые изменения модели и их тесты входят в эту задачу.

Дополнения подключаем по одному. Их управление через меню ещё не готово: перед началом каждой задачи согласуем необходимые запросы и методы подключения с тимлидом. Каждая задача включает работающую функцию, подключение, тесты и PR; внутреннее устройство и имена новых классов выбирает автор с учётом общих контрактов. Пока версия через Stream не готова, работает обычный источник.

## Передача задачи другому участнику

Регулярно отправляем текущую работу в свою ветку и заранее сообщаем о задержках. Если участник не может продолжать, в задаче или PR оставляем:

- ссылку на ветку и список изменённых файлов;
- что работает и как это проверено;
- что осталось сделать, известные ошибки и следующий шаг.

Другой участник продолжает реализацию того же интерфейса. Изменения общих контрактов обсуждаем с тимлидом и авторами зависимых модулей. Задержка отдельного модуля не ломает работающий файловый сценарий, но ручной и случайный ввод обязательны: их нужно доделать или передать другому исполнителю.

## Тимлид и защита

Тимлид организует доступ к репозиторию, задачи, сроки и ревью. Раз в два дня отправляет в чат курса краткий отчёт о готовой работе, текущих задачах и проблемах; о внештатных ситуациях сообщает отдельно. К завершению составляет список участников с результатами работы и оценкой вклада по задачам и PR.

На защите каждый должен объяснить свой код. Показываем успешную работу, неверный ввод и плохой файл. Экран демонстрирует один человек, выступать могут все; на команду отведено не более 20 минут. Перед защитой проводим репетицию. Полные [правила презентации и обязанности тимлида](requirements.md) сохранены отдельно.
