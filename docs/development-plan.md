## Границы ответственности

Автор задачи отвечает за реализацию, тесты и работу функции в приложении. Он должен уметь объяснить свой код. Общие тесты меню не заменяют проверок отдельных источников, компараторов и алгоритмов.

Модули соблюдают существующие интерфейсы. Изменения общего контракта обсуждаем с тимлидом и авторами зависимых частей до начала правок. `Main`, `ConsoleApplication` и `Modules` меняем только там, где этого требует задача. Не переоформляем весь файл и не меняем соседние подключения: так изменения проще объединять.

Алгоритмы получают компаратор извне и не зависят от полей `Car`. Источники используют общий код чтения, генерации и проверки автомобилей. Готовые реализации сортировки и поиска не применяем; ожидаемый порядок в тестах задаём явно.

## Ветки и Pull Request

Изменения сдаём через Pull Request (PR) из рабочей ветки в `main`. PR — запрос на проверку и объединение изменений. Напрямую в `main` код не отправляем.

1. Получить актуальный `main`, создать ветку и закрепить задачу за исполнителем.
2. Реализовать изменение и тесты в той же ветке. Проверить сборку, весь набор тестов и работу изменённой функции через меню.
3. Сохранить изменения коммитами, отправить ветку на GitHub и открыть PR в `main`. В описании указать, что изменилось, как проверено и какие ограничения остались. Назначить тимлида на ревью. Незавершённую работу можно показать в черновом PR.
4. Исправить замечания и повторить необходимые проверки. Новые коммиты отправлять в ту же ветку — они появятся в существующем PR.
5. Если `main` изменился, получить эти изменения в свою ветку, разрешить конфликты и повторить проверки. После ревью тимлид объединяет PR и проверяет общий сценарий.

Задача завершена, когда код соблюдает контракт, тесты проходят, PR проверен, изменения объединены и функция работает в приложении. По [условию](requirements.md) веток с кодом должно быть не меньше участников; к сдаче все рабочие ветки должны быть объединены в `main`.

## Тесты

Все тесты используют JUnit 5. Тестовые классы храним в `test/sorting/` в пакете проверяемого класса: например, `SelectionSortTest` в `test/sorting/algorithm/`. Методы помечаем `@Test` или `@ParameterizedTest`, проверки выполняем через `Assertions`. Пример — [CarAllFieldsComparatorTest](../test/sorting/compare/CarAllFieldsComparatorTest.java).

Имена классов заканчиваем на `Test`, чтобы Maven находил их автоматически. Отдельный `main`, ручные счётчики проверок и общий класс для запуска тестов не нужны. Команды запуска всего набора и отдельного класса приведены в [README](../README.md#тесты).

Проверяем обычную работу, граничные случаи и неверные данные по контракту. При исправлении ошибки добавляем тест, который её воспроизводит. При переработке тестов сохраняем проверяемые сценарии. Для изменения подключения проверяем вызов функции через меню; ручной запуск дополняет автоматические тесты.

Файловые тесты используют временные каталоги. В `examples/` храним только входные данные для демонстрации, без журналов запуска и результатов тестов.

## Передача задачи

Регулярно отправляем текущие коммиты в рабочую ветку. Если участник не может продолжать, он указывает в задаче или черновом PR, что готово, что осталось и какие проверки выполнены. Другой участник продолжает работу по тому же контракту; общие интерфейсы ради передачи не меняем.

## Подготовка защиты

До защиты нужно проверить сценарий демонстрации на компьютере выступающего, распределить объяснение кода и провести командную репетицию с таймером. Репетицию проводим после подготовки материалов.

На демонстрацию отведено не более 20 минут. Показываем успешную работу, неверный ввод и плохой файл. Экран демонстрирует один человек, выступать могут все участники. Сценарий и последовательность действий — в [demo.md](demo.md), полные правила презентации и обязанности тимлида — в [условии](requirements.md).
