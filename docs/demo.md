# Сценарий защиты: действие в приложении → объяснение кода

Для общего обзора сохранён [краткий план демонстрации](demo-outline.md): в нём показ приложения и обзор кода разделены. Ниже — основной подробный сценарий. У этих вариантов разный порядок действий, поэтому каждый проходят с нового запуска приложения.

Выступление строится вокруг работы пользователя: выполняем действие, показываем результат, открываем отвечающий за него метод и объясняем увиденное. Затем переходим к следующему действию. На рассказ и демонстрацию отводим 19 минут, последнюю минуту оставляем на вопросы. Реальное время нужно проверить на командной репетиции.

Экраном управляет один человек. Докладчики могут сменяться между кейсами. Текст в кавычках — основа для рассказа своими словами. Блоки «Для подготовки» помогают разобраться глубже; их не нужно читать целиком во время выступления.

## Подготовка

- Открыть актуальный проект как Maven-проект в IDEA, выбрать JDK 17 или новее. Рабочая папка запуска — корень репозитория. Запускать `Main.main` без аргументов.
- Заранее выполнить `./mvnw clean test` (Windows: `.\mvnw.cmd clean test`), чтобы зависимости уже были скачаны. На защите использовать `./mvnw test`, без `clean`: в `target` будет файл демонстрации.
- Подготовить вкладки или закладки на методы из сценария. В коде показывать только нужный метод, а не прокручивать весь класс. Увеличить шрифт редактора и консоли.
- Для сохранения выбрать отсутствующий файл, например `target/demo-result.txt`. Если он уже существует, использовать другое имя в обоих сохранениях и последующей загрузке. Папка `target` должна существовать после сборки.
- Проверить запуск по README на другом компьютере. Проверить доступность репозитория, слияние рабочих веток в `main` и наличие веток с кодом по числу участников.
- Распределить кейсы между выступающими и пройти весь маршрут с таймером. Подготовка сценария сама по себе не подтверждает, что команда уложилась в срок.

Все пути ниже относительные к корню проекта. Стрелки обозначают последовательность ответов программе: вводить сами стрелки не нужно. Каждый ответ подтверждается Enter. Все основные кейсы выполняются в одном запуске, без перезапуска приложения.

## 1. Запускаем программу и пробуем команды — 0:00–0:45

**В консоли.** Запустить `Main`. Ввести `abc`, затем `99`: программа повторяет запрос. Выбрать `3`, затем `6`: пока нет исходных данных и результата для сохранения. Выбрать `1` → `0`: вернуться из выбора источника в главное меню.

**В коде.** Открыть [Main.main](../src/sorting/app/Main.java), затем в [ConsoleApplication.run](../src/sorting/app/ConsoleApplication.java) показать `while (true)` и `switch`.

**Что сказать.** «Мы выбрали класс Car: мощность, модель и год выпуска. Приложение работает в цикле. Команда запускает действие, после него снова появляется меню. Неверный ввод не завершает программу. Ноль в подменю возвращает назад, а ноль в главном меню завершает работу. Сейчас данных нет — начнём с ручного ввода».

## 2. Создаём автомобили вручную — 0:45–3:00

**В консоли.** Выбрать `1` → `2`. На запрос количества ввести `0`, затем исправить на `2`.

Для первого автомобиля:

| Поле | Сначала ошибка | Затем правильное значение |
| --- | --- | --- |
| Мощность | `-1` | `150` |
| Модель | Пустая строка | `Kia` |
| Год | `1800` | `2020` |

Каждый раз повторяется запрос ошибочного поля. Второй автомобиль: `100`, `Лада`, `2018`. Выбрать `3`: видны ровно две введённые записи.

**В коде.** Открыть [CarConsoleReader.readCar](../src/sorting/source/CarConsoleReader.java): запросы полей и цепочку `new Car.Builder()`. Перейти к [Car.Builder](../src/sorting/model/Car.java): объявление, метод `power`, проверки в `build` и создание `new Car(...)`. Для повторного запроса числа показать цикл в [ConsoleInput.readInt](../src/sorting/input/ConsoleInput.java).

**Что сказать.** «Читатель спрашивает поля одного автомобиля. ConsoleInput преобразует строку в число и проверяет диапазон; при ошибке повторяет запрос. Модель проверяется отдельно: она не должна быть пустой или содержать точку с запятой.

Дальше работает Builder, то есть строитель объекта. `new Car.Builder()` создаёт отдельный объект Builder. Он вложен в Car, а static позволяет создать его без готового автомобиля. Методы power, model и productionYear сохраняют настройки и возвращают тот же Builder через return this — поэтому вызовы соединяются в цепочку. Только build проверяет все значения и создаёт Car. Поля готового автомобиля final, методов их изменения нет.

Проверки в диалоге позволяют удобно исправить ошибку. Builder защищает сам объект: недопустимый автомобиль нельзя создать и из другого источника».

**Сразу связать с тестом.** Показать [CarTest](../test/sorting/model/CarTest.java), методы `builderStoresAllFields` и `rejectsNonPositivePower`: «JUnit вызывает метод с аннотацией Test. assertEquals проверяет сохранённое значение. assertThrows проверяет, что неверные данные действительно отклонены. Параметризованный тест повторяет одну проверку для нескольких значений».

**Для подготовки.** У каждого `new Car.Builder()` свои поля. В объектах Car не хранится по экземпляру Builder: строитель только передаёт значения конструктору. `build()` проверяет положительную мощность, непустую модель без `;` и переводов строк, год от 1900 до текущего включительно. Имя класса через точку обозначает вложенный тип, а не вызов метода Car.

**Переход.** «Теперь получим такую же коллекцию, но без ввода каждого автомобиля».

## 3. Генерируем коллекцию — 3:00–4:15

**В консоли.** Выбрать `1` → `3` → `3`, затем команду `3` для просмотра. Должно быть три корректных автомобиля; конкретные значения случайные.

**В коде.** Открыть [StreamRandomCarSource.load](../src/sorting/source/StreamRandomCarSource.java) и [CarGenerator.get](../src/sorting/source/CarGenerator.java). Рядом показать короткий конвейер в [StreamManualCarSource.load](../src/sorting/source/StreamManualCarSource.java). В [MyArrayList](../src/sorting/collection/MyArrayList.java) показать внутренний массив, `size`, `add` и `grow`.

**Что сказать.** «В generate передан генератор одного автомобиля. limit ограничивает их количество, а collect собирает результат в нашу коллекцию. Автомобили создаются при выполнении этого конвейера, а не загружаются заранее в готовый список. Генератор также использует Builder.

У collect три действия: создать контейнер, добавить элемент и объединить контейнеры. Здесь обработка последовательная. В ручном источнике тот же принцип: для каждой позиции mapToObj вызывает чтение одного автомобиля, collect собирает их в список. MyArrayList хранит ссылки в обычном массиве; когда места не хватает, создаёт массив вдвое больше и переносит ссылки. Своя коллекция нужна для дополнительного задания 3*. Stream — способ обработки данных; его наличие ещё не означает многопоточность».

**Для подготовки.** Ручной источник тоже использует Stream: [StreamManualCarSource.load](../src/sorting/source/StreamManualCarSource.java) берёт `IntStream.range(0, length)`, для каждого элемента вызывает чтение автомобиля через `mapToObj` и собирает результат через `collect`. Диалог идёт последовательно с общим ConsoleInput. В [StreamRandomCarSourceTest.generatedCarsHaveValidValues](../test/sorting/source/StreamRandomCarSourceTest.java) проверяются размер и допустимость случайных данных, а не заранее угаданная последовательность.

**Переход.** «Для сравнения алгоритмов удобнее фиксированный набор. Загрузим его из файла и посмотрим, почему меню может работать с разными источниками».

## 4. Загружаем файл и проверяем ошибки — 4:15–6:15

**В консоли.** `1` → `1` → `examples/cars-sort.txt` → `6`, затем `3`. В файле шесть автомобилей; два из них — `150;Kia;2018`.

**В коде.** Показать [DataSource.load](../src/sorting/contract/DataSource.java), три метода источников в [Modules](../src/sorting/app/Modules.java) и `source.load(length)` в [ConsoleApplication.loadCars](../src/sorting/app/ConsoleApplication.java). Затем открыть [StreamFileCarSource.load](../src/sorting/source/StreamFileCarSource.java) и [CarLineParser.parse](../src/sorting/source/CarLineParser.java).

**Что сказать.** «Все источники соблюдают один контракт: load принимает длину и возвращает MyArrayList с таким количеством автомобилей. Modules создаёт нужный источник. Меню вызывает общий метод и получает одинаковый тип результата.

В файле одна строка — один автомобиль: мощность, модель и год через точку с запятой. Files.lines читает UTF-8, map разбирает строки, collect собирает автомобили. Парсер проверяет число полей и преобразует числа, а значения снова проверяет Builder. Ручной, случайный и файловый ввод сходятся в одной модели».

**В консоли — два отрицательных кейса.**

1. `1` → `1` → `examples/cars-invalid.txt` → `1`: ошибка второй строки, хотя запрошена одна запись.
2. `1` → `1` → `examples/cars-sort.txt` → `7`: требуется семь автомобилей, найдено шесть.
3. `3`: прежние шесть автомобилей остались доступны.

**В коде и в речи.** Показать ограничение `result.size() < length` внутри `collect` и присваивания после `source.load(length)` в меню: «Мы ограничиваем число сохраняемых автомобилей, но разбираем весь файл. Поэтому ошибка за пределами нужного количества тоже обнаруживается. Новая коллекция заменяет старую только после успешного load. При ошибке до присваивания выполнение не доходит».

**Для подготовки.** `CarLineParser` использует `split(";", -1)`, чтобы сохранить пустое последнее поле. Файловый источник добавляет номер строки к сообщению об ошибке; поток строк закрывается через try-with-resources. В [StreamFileCarSourceTest.validatesLinesAfterRequestedPrefix](../test/sorting/source/StreamFileCarSourceTest.java) закреплён кейс с ошибкой после запрошенных записей. Конвейер файла рассчитан на последовательную обработку: простая замена на parallel нарушит предположения о нумерации строк и ограничении размера внутри накопителя.

**Переход.** «Данные получили. Теперь независимо выберем, как их сравнивать и каким алгоритмом переставлять».

## 5. Меняем алгоритмы и правила сравнения — 6:15–10:00

### Все три поля и сортировка вставками

**В консоли.** `2` → `1` → `1` → `4`.

```text
100;Volvo;2022
150;Audi;2022
150;Kia;2018
150;Kia;2018
150;Kia;2022
200;Audi;2010
```

**В коде.** Открыть [CarAllFieldsComparator.compare](../src/sorting/compare/CarAllFieldsComparator.java): проверки мощности, затем модели, затем года. В [InsertionSort.sort](../src/sorting/algorithm/InsertionSort.java) показать вызов `comparator.compare(...) > 0` и сдвиг элементов.

**Что сказать.** «Компаратор сравнивает два автомобиля. Отрицательный результат означает, что первый должен идти раньше, положительный — позже, ноль — что выбранные признаки равны. Здесь сначала учитывается мощность. При равной мощности сравниваем модель, при одинаковой модели — год. Поэтому Audi с мощностью 150 раньше Kia, а Kia 2018 года раньше Kia 2022 года. Приоритет выбран в проекте; условие его не задаёт.

Алгоритм сам этих полей не знает. Сортировка вставками берёт очередной элемент, сдвигает большие элементы вправо и вставляет его на освободившееся место. Что значит больше, ей сообщает компаратор».

### Меняем стратегию и компаратор независимо

Выполнить ещё три сортировки без повторной загрузки файла. После каждой коротко показать отвечающий за неё код.

| Команды из главного меню | Что увидим | Что открыть и сказать |
| --- | --- | --- |
| `2` → `2` → `2` → `4` | Мощности `100, 150, 150, 150, 150, 200` | [SelectionSort.sort](../src/sorting/algorithm/SelectionSort.java), поиск `minIndex`: «Выбором находим минимум оставшейся части и ставим на очередное место». [CarPowerComparator](../src/sorting/compare/CarPowerComparator.java): сравнивает только мощность |
| `2` → `3` → `3` → `4` | Модели `Audi, Audi, Kia, Kia, Kia, Volvo` | [BubbleSort.sort](../src/sorting/algorithm/BubbleSort.java), обмен соседей: «Пузырьком меняем соседей, если они стоят неправильно; после прохода сокращаем область по последнему обмену». [CarModelComparator](../src/sorting/compare/CarModelComparator.java): сравнивает только модель |
| `2` → `1` → `4` → `4` | Годы `2010, 2018, 2018, 2022, 2022, 2022` | [CarProductionYearComparator](../src/sorting/compare/CarProductionYearComparator.java): «Алгоритм снова вставками, но правило сравнения теперь другое — год» |

При сравнении одного поля остальные поля не участвуют. В частности, равная мощность не обязывает сортировать такие автомобили ещё и по году. Модели сравниваются через `String.compareTo`, с учётом регистра.

**В коде.** Показать [SortStrategy](../src/sorting/contract/SortStrategy.java) и три метода алгоритмов в [Modules](../src/sorting/app/Modules.java). В `ConsoleApplication.sortCars` показать:

```java
MyArrayList<Car> result = cars.copy();
strategy.sort(result, comparator);
sortedCars = result;
```

**Что сказать.** «Это паттерн Strategy: три реализации одного интерфейса SortStrategy. Во время работы пользователь выбирает реализацию, а меню вызывает один метод sort. Компаратор задаёт порядок, стратегия выполняет перестановки. Готовые сортировки не используются.

Чтобы добавить четвёртый алгоритм, напишем реализацию SortStrategy и тесты, добавим фабрику в Modules и выбор в меню. Источники и компараторы менять не потребуется. Если нужен ещё один вариант сравнения существующих полей, добавим компаратор и его пункт, сохранив все алгоритмы».

**В консоли.** Выбрать `3`: исходный порядок прежний. Выбрать `2` → `0`, затем `4`: отмена не потеряла предыдущий результат.

**Объяснить сохранность.** «Каждая сортировка начинается с копии исходной коллекции. copy создаёт отдельный контейнер с теми же ссылками на неизменяемые Car. Алгоритм переставляет ссылки в копии. Новый результат сохраняется только после успеха».

**Для подготовки.** [InsertionSortTest.sortsCarsByAllFieldsAndPreservesReferencesAndOriginal](../test/sorting/algorithm/InsertionSortTest.java) проверяет порядок, размер, ссылки, повторы и сохранность оригинала. [CarAllFieldsComparatorTest](../test/sorting/compare/CarAllFieldsComparatorTest.java) отдельно проверяет приоритет каждого поля. Четыре показанных запуска покрывают все пункты выбора, но не все 12 комбинаций алгоритма и компаратора; не выдавать их за полную переборную проверку.

**Переход.** «В исходной коллекции есть одинаковые автомобили. Посчитаем их в нескольких потоках».

## 6. Считаем совпадения — 10:00–11:30

**В консоли.** `5` → `150` → `Kia` → `2018` → на число потоков сначала `0`, затем `3`. Результат — `Найдено совпадений: 2`.

**В коде.** В [CarCounter](../src/sorting/source/CarCounter.java) показать `countInThread`, создание `Thread`, вызовы `start`, `join` и суммирование `counts`.

**Что сказать.** «Совпадение — равенство всех трёх полей автомобиля, а не одной мощности. Подсчёт использует исходную коллекцию и не требует сортировки.

У нас шесть элементов и три рабочих потока. Индексы начинаются с нуля: первый проверяет 0 и 3, второй — 1 и 4, третий — 2 и 5. Это задаёт цикл с шагом threadCount. Каждый элемент проверяется один раз, результаты здесь 0, 1 и 1.

start запускает поток. Каждый записывает число в свою ячейку counts, поэтому общего увеличиваемого счётчика нет. join дожидается завершения; после ожидания складываем результаты и получаем два. Коллекция во время подсчёта только читается. На шести элементах ускорение не обещаем — показываем устройство многопоточного подсчёта».

**Снова в консоли.** `5` → `150` → `Kia` → `2017` → `3`: теперь результат `0`, поскольку автомобиля с таким сочетанием полей нет.

**Для подготовки.** В [CarCounterTest.testCount](../test/sorting/source/CarCounterTest.java) один сценарий запускается с разным числом потоков. Проверяются также пустая коллекция, отсутствие совпадений, некорректные аргументы и прерывание до начала работы. Если ожидание прервано во время выполнения, `stopThreads` посылает рабочим потокам `interrupt` и ждёт их завершения; частичное число не возвращается. Число потоков в меню ограничено диапазоном 1–255. `Arrays.stream(counts).sum()` суммирует результаты, а многопоточность создают именно Thread.

**Переход.** «Теперь используем те же алгоритмы для более специального правила: переставлять только автомобили с чётной мощностью».

Выбрать `7` → `3` → `4`:


**Что сказать.** «Modules — обычный класс, где собраны методы создания модулей. Здесь carResultWriter создаёт CarFileWriter. Меню получает его через интерфейс ResultWriter и вызывает append. Меню спрашивает путь и показывает сообщение, а работа с файлом находится в отдельном классе. APPEND дописывает данные, поэтому первая пятёрка записей сохранилась.

Это сокращённая версия [памятки с объяснением Modules](presentation.md). На выступлении показать существующую запись; пример возможной замены не представлять как уже реализованный модуль.

## Дополнительные проверки для репетиции и вопросов

Основной маршрут показывает все доступные функции и варианты меню. Граничные ситуации ниже дополняют его; не нужно превращать выступление в перебор всех возможных входных данных.

| Ситуация | Как проверить и какой результат ожидать |
| --- | --- |
| Попытка сортировки без коллекции | В новом запуске `2` → `1`: просьба сначала загрузить автомобили |
| Неверный путь входного файла | Загрузка по отсутствующему пути с положительной длиной: ошибка, прежние данные сохранены |
| Ошибка загрузки после сортировки | Получить результат, загрузить `cars-invalid.txt`, затем `3` и `4`: сохранены и исходник, и результат |
| Модель с разделителем | В ручном вводе `BMW;X`: повторный запрос модели |
| Число не помещается в int, будущий год | Повторный запрос соответствующего поля, без завершения меню |
| Отмена выбора компаратора | При загруженных данных `2` → `1` → `0`: главное меню, прежний результат сохранён |
| Пустой путь записи | При готовом результате `6` и пустая строка: сообщение об ошибке пути |
| Файл без последнего перевода строки | Тест `CarFileWriterTest.separatesNewRecordsWhenFileHasNoFinalNewline` показывает разделение старой и новой записи |
| Прерывание ввода до команды выхода | `MainTest.reportsUnexpectedEndOfInputAndExitsWithError` проверяет сообщение и код завершения 1; это техническая ошибка ввода, а не ещё одна команда меню |

Правила защиты и обязанности тимлида сохранены в [постановке](requirements.md).
