# Каркас приложения и его готовность

Каркас в этом проекте — минимальная работающая консольная программа, которую команда сможет запустить и расширять по готовому примеру. Она загружает автомобили из файла, сортирует их одним алгоритмом по одному правилу, показывает результат и возвращается в меню.

Интерфейсы входят в каркас как договоры между модулями. Для готовности нужен весь работающий сценарий: **запуск → загрузка файла → сортировка → результат → повторное действие или выход**.

Тимлид готовит каркас небольшими законченными шагами. Затем четыре участника добавляют остальные источники, компараторы и алгоритмы. Дополнительные задания начинаются после основной части. Задачи каждого перечислены в [плане разработки](development-plan.md).

## Что входит в каркас

| Часть | Что должно работать | Классы и интерфейсы |
| --- | --- | --- |
| Запуск | Приложение открывается в IntelliJ IDEA и запускается из терминала | `Main` |
| Консольный интерфейс | Меню работает в цикле, принимает команды и обрабатывает неверный ввод | `ConsoleApplication`, `ConsoleInput` |
| Модель | Автомобиль создаётся через Builder; недопустимые поля отклоняются | `Car`, `Car.Builder` |
| Коллекция | Автомобили хранятся в общем контейнере; для сортировки можно получить копию | `MyArrayList<Car>` |
| Один источник | Пользователь указывает путь и длину; файл проверяется и загружается | `DataSource<Car>`, `FileCarSource`, `CarLineParser` |
| Один компаратор | Два автомобиля сравниваются по всем трём полям | `CarAllFieldsComparator` |
| Один алгоритм | Коллекция сортируется собственным алгоритмом вставок | `SortStrategy<T>`, `InsertionSort<T>` |
| Вывод | Можно увидеть исходные данные и результат | `ConsoleApplication` |
| Подключение модулей | Выбор конкретного источника, компаратора и алгоритма находится в одном месте | `Modules` |
| Проверки и примеры | Есть тесты, пример правильного и плохого файла, команды запуска | `test/`, `examples/`, README |

Это целевой состав. Текущая готовность указана ниже; наличие класса в таблице не означает, что его код уже написан.

CLI — консольный интерфейс: пользователь вводит команды и получает текстовый ответ. Для нашего приложения это интерактивное меню. Его минимальные действия:

1. Загрузить автомобили из файла: запросить путь и положительное количество записей.
2. Отсортировать загруженные автомобили.
3. Показать исходную коллекцию.
4. Показать последний результат сортировки.
5. Выйти по отдельному пункту меню.

При неверной команде, длине или ошибке файла программа объясняет причину и позволяет продолжить. Попытка сортировать до загрузки данных должна давать понятное сообщение.

## Пример для команды

Первый источник — `FileCarSource`. Формат: UTF-8, одна запись `мощность;модель;год` на строку. Проверка файла и поведение при лишних или недостающих записях определены в [архитектуре](architecture.md#формат-файла). Разбор одной строки выполняет `CarLineParser`, а проверку значений модели — Builder.

Первый компаратор — `CarAllFieldsComparator`. Порядок: сначала мощность; при равенстве — модель; при равенстве модели — год. Модель сравнивается с учётом регистра. Это сразу задаёт базовый порядок по всем трём полям.

Первый алгоритм — `InsertionSort<T>`, сортировка вставками. Он получает `Comparator<T>` и не обращается к полям `Car`. Поэтому участники смогут использовать его с другими правилами сравнения.

`Modules` будет обычным классом выбора реализаций. `Main` подключит через него компоненты к консольному приложению. После готовности нового модуля тимлид добавит его к доступным вариантам. Авторы источников и алгоритмов работают в своих классах; общую логику меню менять каждому не требуется.

Готовый каркас станет примером подключения одного источника, компаратора и стратегии. Тесты этого примера покажут, как проверять следующие реализации.

## Что остаётся за пределами первого каркаса

На следующем этапе команда добавляет ручной и случайный источники, три компаратора по отдельным полям и ещё два алгоритма. Только после этого проверяем основную часть целиком.

Версия с одним файловым источником ещё не выполняет всё основное задание: ручное и случайное заполнение тоже обязательны. Количество алгоритмов в условии не задано; три алгоритма — решение команды для распределения практической работы.

Чётный режим, добавление результатов в файл, заполнение через Stream и многопоточный подсчёт относятся к следующему этапу. Их отсутствие не должно мешать загрузке, обычной сортировке и выводу. Готовность каркаса не зависит от реализации этих дополнений.

Собственное равенство `Car.equals` и `hashCode` потребуется перед подключением подсчёта совпадений. Для первого сценария сортировки достаточно компаратора.

## Почему используется собственная коллекция

Собственная коллекция требуется только в [дополнительном пункте 3*](requirements.md#3-заполнение-через-stream). Для основной части допустим стандартный `ArrayList`; запрет готовой сортировки не запрещает готовые контейнеры.

В проекте уже реализован и проверен `MyArrayList<T>`, а интерфейсы модулей используют этот тип. Оставляем его текущим общим контейнером. Это заранее подготовленная часть дополнения, а не обязательное условие любого каркаса. Заполнение через Stream и проверка всей связки для задания `3*` ещё предстоят.

## Когда каркас готов к передаче

- Проект собирается из свежей копии по командам README и запускается в IntelliJ IDEA.
- Пользователь задаёт путь и длину; правильный файл даёт ровно запрошенное число автомобилей.
- Неверные команды и длины, отсутствующий, повреждённый и слишком короткий файл обрабатываются без потери прежних данных.
- Сортировка работает по всем трём полям с указанным приоритетом, сохраняет состав коллекции и её размер.
- Исходная коллекция сохраняется; сортировка работает с копией контейнера. Неудачная операция не уничтожает предыдущий успешный результат.
- После действия программа снова принимает команду; обычное завершение выполняется пунктом выхода.
- Тесты модели, коллекции, чтения файла, компаратора, алгоритма и сценария целиком проходят.
- В `examples/` есть входные файлы и фактические результаты успешного и ошибочного сценариев.
- Участникам понятны свои интерфейсы, файлы и способ подключения. Изменения каркаса проверены и объединены в `main`.

## Текущее состояние

Уже работают `Car` с Builder, `MyArrayList<T>` и демонстрационный `Main`, который создаёт один автомобиль. Есть пять интерфейсов и ручные тесты модели и коллекции.

Консольный цикл, файловый источник, первый компаратор, сортировка и подключение через `Modules` ещё не реализованы. Поэтому работающий каркас пока не готов. Ближайшие порции: консольный цикл, затем файловый источник, затем один компаратор и один алгоритм с проверкой всего сценария.
