# Общие договоры модулей

Общие договоры фиксируют имена методов, типы параметров и ожидаемый результат. Интерфейс задаёт договор; класс участника пишет его реализацию. Это часть [работающего каркаса](scaffold.md), который включает меню и полный сценарий загрузки и сортировки. Наличие интерфейса ещё не означает, что функция готова.

Сейчас работают `Car` с Builder, общая коллекция `MyArrayList<T>`, меню, файловый источник и сортировка вставками. В `sorting.contract` добавлены пять интерфейсов. Через `Modules` подключены `FileCarSource` как `DataSource<Car>`, `InsertionSort<Car>` как `SortStrategy<Car>` и составной компаратор. Остальные основные реализации добавят участники. Дополнения идут после основной части.

## Общая коллекция

`MyArrayList<T>` — собственный контейнер, одинаковый для всех модулей. `T` обозначает тип элементов: например, `MyArrayList<Car>` или `MyArrayList<Integer>`. При заполнении внутреннего массива контейнер увеличивает его размер. Собственная коллекция требуется в дополнительном пункте `3*`; здесь используется уже готовая реализация проекта. Для основной части условие допускает стандартные коллекции.

| Метод | Договор |
| --- | --- |
| `add(item)` | Добавляет элемент в конец |
| `get(index)` | Возвращает элемент по индексу |
| `set(index, item)` | Заменяет элемент; размер не меняется |
| `size()` | Возвращает количество элементов |
| `isEmpty()` | Проверяет, нет ли элементов |
| `copy()` | Возвращает отдельный контейнер с теми же ссылками на элементы |

Индексы допустимы от `0` до `size() - 1`. Для неверного индекса `get` и `set` выбрасывают `IndexOutOfBoundsException`. Методы `add` и `set` отклоняют `null` с `NullPointerException`. Это не ввод пользователя, а ошибка использования контейнера в коде.

Копия независима по составу и порядку элементов: её `add` и `set` не меняют исходный контейнер. Сами объекты не копируются; неизменяемый `Car` можно безопасно хранить в обоих контейнерах.

Коллекция не рассчитана на одновременную запись из нескольких потоков. Во время многопоточного подсчёта она должна оставаться неизменной.

## Интерфейсы

| Интерфейс | Метод | Где будет реализация |
| --- | --- | --- |
| `SortStrategy<T>` | `sort(items, comparator)` | Основные алгоритмы: `InsertionSort<T>`, `SelectionSort<T>`, `BubbleSort<T>` |
| `DataSource<T>` | `load(length)` | Обычные источники и версии через Stream |
| `EvenSorter<T>` | `sort(items, field, strategy)` | Участник 2: `EvenValueSort<T>` |
| `ResultWriter<T>` | `append(items, path)` | Участник 3: `CarFileWriter` |
| `OccurrenceCounter<T>` | `count(items, target, threadCount)` | Участник 5: `ParallelOccurrenceCounter<T>` |

Распределение дополнительных модулей в таблице предварительное; перед этапом дополнений команда подтверждает его по [плану разработки](development-plan.md).

Все ссылочные параметры этих методов обязательны: `null` отклоняется с `NullPointerException`. Проверки должен написать автор реализации; интерфейс не выполняет их автоматически. Исключения передаются вызывающему коду, а не заменяются фиктивным успешным результатом.

### Сортировка

`SortStrategy<T>` получает коллекцию и `Comparator<T>` — правило сравнения двух элементов. Алгоритм меняет порядок внутри переданной коллекции. Размер, ссылки на элементы и число повторений сохраняются. Пустая коллекция и один элемент допустимы; порядок элементов, равных по компаратору, пока не фиксируется.

Первая реализация — `InsertionSort<T>`. Оба аргумента обязательны даже для пустой коллекции. Меню передаёт алгоритму копию исходного контейнера и сохраняет её как результат только после успеха. При исключении уже начатая сортировка может изменить переданный контейнер; восстановление его состояния не входит в договор алгоритма. Благодаря отдельной копии прежние данные меню сохраняются.

Уже реализован `CarAllFieldsComparator` — стандартный `Comparator<Car>` с порядком мощность, модель, год. Числа сравниваются по возрастанию, модели — через `String.compareTo` с учётом регистра. К следующему полю переходим только при равенстве предыдущих. Метод отклоняет `null` с `NullPointerException`; `0` означает совпадение всех трёх полей, независимо от ссылок на объекты. Участники добавят отдельные `CarPowerComparator`, `CarModelComparator` и `CarProductionYearComparator`. Каждый автор работает в своём файле. Алгоритм не должен обращаться к полям автомобиля напрямую.

### Источник данных

`DataSource<T>.load(length)` возвращает новую коллекцию ровно из `length` проверенных элементов. Неположительная длина — `IllegalArgumentException`, ошибка чтения — `IOException`. Укороченный результат нельзя выдавать за успешную загрузку.

Откуда читать, источник получает при создании своей реализации: например, файловый источник — путь к файлу, ручной — общий читатель консоли. Метод `load` остаётся одинаковым для всех способов заполнения. Формат и проверка файла описаны в [архитектуре](architecture.md#формат-файла).

`FileCarSource` получает `Path` через конструктор. При плохой строке или нехватке записей выбрасывает `IllegalArgumentException`; при проблеме чтения, включая неправильный UTF-8, — `IOException`. Метод проверяет весь файл и возвращает первые `length` автомобилей только при успешной проверке.

Обычные и Stream-источники реализуют один интерфейс. Общий `ConsoleInput` уже готов: `readLine(prompt)` читает одну строку, `readInt(prompt, min, max)` запрашивает целое число в заданных границах. Оба метода передают ошибки чтения через `IOException`, конец ввода — через его подтип `EOFException`. Готов и `CarLineParser.parse(line)`: возвращает один `Car`, при неверном формате или значениях выбрасывает `IllegalArgumentException`, при `null` — `NullPointerException`. Номер строки к ошибке добавляет файловый источник. На этапе расширения основной части участник 2 добавит `CarConsoleReader`, а участник 3 — `CarGenerator`. Эти средства затем будут общими для обычных источников и версий через Stream.

### Чётный режим

`EvenSorter<T>` получает коллекцию, `ToIntFunction<T>` и обычную стратегию сортировки. `ToIntFunction<T>` — функция получения целого числового значения из элемента; для автомобиля это будет мощность.

Модуль выбирает элементы с чётным значением, сортирует их по возрастанию этого значения переданной стратегией и возвращает на соответствующие места. Объекты с нечётным значением сохраняют свои индексы. Пустая коллекция допустима.

К началу дополнений основные алгоритмы уже готовы. Участник проверяет чётный режим с каждой подключённой реализацией `SortStrategy<T>`, а также сохранение нечётных объектов на исходных индексах.

### Запись в файл

`ResultWriter<T>.append(items, path)` добавляет записи в конец файла, при необходимости создавая его. Коллекция не изменяется. `Path` — тип Java для пути к файлу. Ошибки записи передаются через `IOException`.

`CarFileWriter` будет реализовывать `ResultWriter<Car>`: UTF-8, формат `мощность;модель;год`, одна запись на строку. Если прежний файл не заканчивается переводом строки, новую запись нужно начать с новой строки.

### Подсчёт

`OccurrenceCounter<T>.count(items, target, threadCount)` возвращает количество элементов, равных образцу `target` через `equals`. Пустая коллекция даёт `0`; положительное число потоков обязательно даже для неё. Реализация использует не больше указанного числа рабочих потоков и не меняет коллекцию.

Метод может выбросить `InterruptedException`, если выполнение прервано. Перед выходом нужно завершить запущенных работников. Ошибку или частичный результат нельзя выдавать за полный подсчёт.

У `Car` пока нет своего `equals` и `hashCode`: два отдельно созданных автомобиля с одинаковыми полями ещё не считаются равными. Тимлид подготовит это правило перед подключением подсчёта; для каркаса с сортировкой оно не требуется. До его готовности универсальный счётчик можно проверять на `Integer` или `String`; проверку совпадающих полей разных `Car` нужно добавить после подготовки равенства.

## Как начать и как заменять реализацию

Автор создаёт свой класс с `implements` нужного интерфейса и пишет собственные тесты. Файлы `Car`, коллекции и общих интерфейсов не нужно менять ради своей реализации. Изменение договора согласуется со всеми, кто его использует.

Если участник не может продолжить, другой человек реализует тот же интерфейс и продолжает его тесты. Переписывать остальные модули из-за смены исполнителя не требуется.

Сейчас `Main` запускает цикл меню и передаёт ему `Modules`. Команда загрузки получает через `Modules.fileSource(path)` реализацию `DataSource<Car>` и вызывает `load(length)`. Команда сортировки получает `SortStrategy<Car>` через `sortStrategy()` и `Comparator<Car>` через `carComparator()`, затем вызывает `sort` на копии исходной коллекции. Просмотр исходных данных и результата выполняется отдельными пунктами. Для новых реализаций тимлид расширит выбор в `Modules` и меню; договоры источника и алгоритма сохраняются.
