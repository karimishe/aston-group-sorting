# Требования к групповому проекту

## Основное задание

Разработать Java-приложение для сортировки объектов **одного выбранного класса**. Можно выбрать класс из примеров ниже или предложить свой.

| Класс | Три поля |
| --- | --- |
| Автобус | Номер, модель, пробег |
| Пользователь | Имя, пароль, почта |
| Студент | Номер группы, средний балл, номер зачётной книжки |
| Автомобиль | Мощность, модель, год производства |
| Бочка | Объём, хранимый материал, материал изготовления |

Обязательные требования к приложению:

- Программа работает в цикле. Выход из цикла возможен только по соответствующему выбору пользователя.
- Пользователь выбирает длину исходного массива и способ его заполнения: **из файла, случайными данными или вручную**.
- Для вводимых данных, включая данные из файла, выполняется валидация — проверка корректности.
- В программе применяется паттерн **«Стратегия»**.
- Выбранный класс имеет собственную реализацию паттерна **Builder**.
- Базовая сортировка реализуется **по всем трём полям** выбранного класса. Для кастомной сортировки разрешено использовать компаратор.
- Запрещено применять готовые реализации сортировки, поиска и паттернов.
- Архитектура и стиль кода соответствуют конвенциям Java.
- Для написанного кода реализуются тесты. Тестовые библиотеки разрешены, но необязательны: достаточно собственных проверок в отдельных классах.

## Дополнительные задания

Эти возможности перечислены отдельно от основного задания.

### 1. Сортировка элементов с чётным значением

Дополнительно к основным сортировкам реализовать те же алгоритмы для сортировки по какому-либо числовому полю: объекты с чётными значениями этого поля сортируются в натуральном порядке, а объекты с нечётными значениями остаются на исходных позициях.

### 2. Запись результатов в файл

Реализовать запись отсортированных коллекций / найденных значений в файл **в режиме добавления данных**.

### 3. Заполнение через Stream

Заполнять коллекции посредством стримов.

**3\*. Собственные коллекции:** коллекции для заполнения должны быть кастомными.

### 4. Многопоточный подсчёт

Реализовать многопоточный метод, который подсчитывает количество вхождений элемента `N` в коллекцию и выводит результат в консоль.

## Репозиторий и сдача

- Проект размещается на GitHub или GitLab.
- Количество веток с кодом должно быть не меньше количества участников.
- Все ветки в итоге объединяются в `master` / `main`.
- Результат сдаётся **ссылкой на репозиторий GitHub / GitLab**.

## Защита проекта

Презентация проходит на последней лекции курса. На одну команду отводится **не более 20 минут**.

Необходимо:

1. Рассказать, что делает проект и какие функции реализованы, показать соответствующие участки кода.
2. Организовать рассказ либо от лица одного участника, либо с выступлением каждого о своей части. В обоих случаях демонстрацией экрана управляет **один человек**.
3. Показать положительные сценарии и отрицательные: **невалидный ввод пользователя и файл с плохими данными**.

## Обязанности тимлида

1. Собрать команду из участников интенсива: **5 человек, включая тимлида**.
2. Создать репозиторий на GitHub / GitLab и добавить всех членов команды контрибьюторами.
3. Декомпозировать общую задачу — разделить её на задачи проекта; это можно сделать вместе с командой.
4. Обеспечить команду задачами.
5. Следить за работой команды и соблюдением установленных сроков разработки.
6. **Раз в два дня** предоставлять краткий отчёт о работе команды в соответствующую тему общего чата курса.
7. Сообщать обо всех внештатных ситуациях в работе команды.
8. По итогам работы составить список участников с результатами выполненной работы и оценкой производительности.

## Проектные решения

Конкретный класс, алгоритмы, приоритет полей при сравнении, формат входного файла и распределение задач команда определяет отдельно. Примеры классов выше не означают, что требуется реализовать их все.
